# Rendering Architecture

Sauerbraten Revival — rendering strategy. This document explains the ArrayMesh +
RenderingServer approach and how it interplays with collision, the octree, and
the OGZ import pipeline.

## Decision: Delegate rendering to Godot

We do **not** reimplement Sauerbraten's renderer. Instead:

1. **Octree** → thin in-memory data structure (geometry + surface info).
2. **Mesher** → traverses octree, emits `ArrayMesh` per chunk.
3. **RenderingServer** → receives meshes directly (low-level, no scene tree overhead).
4. **Godot Forward+** → renders with built-in lighting, shadows, reflections, LOD.

This is the opposite of a custom GL renderer. We leverage Godot's mature pipeline.

---

## Why ArrayMesh + RenderingServer?

### Benefits

| Benefit | Explanation |
| --- | --- |
| **Thin octree** | Octree stores only geometry + face metadata; no VBOs, no GL state. |
| **Native Godot integration** | Materials, shaders, lightmaps, GI — all first-class. |
| **Built-in LOD** | `ArrayMesh.add_lod()` + automatic distance-based switching. |
| **Automatic culling** | Frustum culling, occlusion culling handled by the engine. |
| **TOOL support** | Meshes update in the editor — live preview without Play mode. |
| **No shader maintenance** | Standard PBR path works; custom shaders only for Sauer-specific blending. |
| **Future-proof** | Benefits from Godot renderer improvements (Vulkan, mobile, etc.). |

### Drawbacks

| Drawback | Mitigation |
| --- | --- |
| Mesh upload cost | Chunk updates require GPU upload; budget per-frame updates. |
| No custom occlusion | Godot's GPU-based occlusion culling is different from Sauer's octree-based approach; likely comparable or better on modern GPUs. |
| Material mapping | Sauer's `Slot`/`VSlot` system must map to Godot materials; one-time conversion work. |
| Lightmap format | Sauer's packed lightmaps need conversion to Godot `LightmapGI` or baked textures. |
| Blend/detail shaders | Multi-layer blending requires a custom shader; doable but not free. |
| Memory overhead | Godot mesh structures are slightly larger than raw VBOs; negligible on modern systems. |

### Performance assessment

**Verdict: Good enough, likely better.**

- Sauerbraten targets ~2006 hardware with OpenGL 2.x.
- Godot Forward+ on Vulkan/modern GL is dramatically faster.
- LOD + frustum culling + occlusion culling handle large maps well.
- Incremental chunk updates avoid full-map rebuilds.
- The original "feel" depends on movement and collision, not raw FPS — and we'll
  exceed the original's frame rate easily.

## Chunking strategy

The world is divided into **chunks** for incremental updates:

```
Chunk size: 32³ leaf cubes (tunable)
Each chunk → one ArrayMesh instance
Dirty tracking: bitmask or set of modified chunk IDs
Per-frame budget: max N chunk rebuilds/frame (e.g., 2-4)
```

When an octree mutation occurs:
1. Mark affected chunks dirty.
2. Each frame, rebuild up to N dirty chunks.
3. Upload new ArrayMesh to RenderingServer.
4. Clear dirty flag.

This spreads large edits across frames, avoiding hitches.

## Collision detection

**Rendering and collision are decoupled.**

| Concern | Mechanism |
| --- | --- |
| Rendering | ArrayMesh → RenderingServer (GPU) |
| Collision | Direct octree traversal (CPU) — ported from `physics.cpp` |

We do **not** use Godot's physics shapes for world collision. Reasons:

1. **Fidelity**: The original movement feel depends on exact collision code.
2. **Performance**: Octree traversal is O(log n); generating trimesh shapes is expensive.
3. **Mutability**: Octree updates instantly affect collision; no shape rebuild needed.
4. **Proven**: The original collision code is battle-tested.

The octree simultaneously serves:
- Collision queries (`move`/`collide`/`clipbox`).
- Mesh generation (faces → triangles → ArrayMesh).
- Spatial queries (raycasts, visibility).

Godot physics (Jolt) is used only for entities (players, projectiles, mapmodels).

## LOD integration

Godot's `ArrayMesh` supports multiple LOD levels:

```csharp
ArrayMesh mesh = new();
mesh.AddSurfaceFromArrays(Mesh.PrimitiveType.Triangles, fullDetailArrays);
mesh.AddLod(distanceThreshold, simplifiedIndices);
```

For octree geometry, LOD can be generated by:
1. Skipping small cubes at distance (effective "remip" for rendering).
2. Using a mesh simplification pass (Godot's `SurfaceTool.GenerateLod`).
3. Pre-computing LOD levels during chunk meshing.

The octree's hierarchical nature naturally supports LOD — larger parent cubes
are lower detail.

## Material pipeline

### Original Sauer system

```
Slot (base definition):
  - sts[]: texture layers (diffuse, normal, glow, etc.)
  - shader: assigned shader
  - params[]: shader parameters

VSlot (variant):
  - scale, rotation, offset, scroll
  - colorscale, glowcolor
  - layer (blending)
  - alphafront, alphaback
```

### Godot mapping

| Sauer concept | Godot equivalent |
| --- | --- |
| Slot | `ShaderMaterial` or `StandardMaterial3D` |
| VSlot variant | Material instance with overridden uniforms |
| Texture layers | Albedo, normal, emission textures |
| Blending | Custom shader with blend mask |
| Lightmap | `LightmapGI` or baked texture channel |

The material manifest maps face indices → Godot materials. This is resolved at
import time, not runtime.

---

## Staged fidelity (from architecture.md)

1. **Approximate**: Base texture + tint, dynamic Godot lighting.
2. **Blended**: Multi-layer material blending, per-face UVs.
3. **Exact**: Original lightmaps, envmaps, decals, full surface model.

The ArrayMesh approach supports all three stages — only the materials/shaders change.

## RenderingServer usage

For maximum performance, meshes are streamed directly to RenderingServer:

```csharp
// Create mesh RID (once per chunk)
Rid meshRid = RenderingServer.MeshCreate();

// Add surface from arrays
RenderingServer.MeshAddSurfaceFromArrays(meshRid, 
    RenderingServer.PrimitiveType.Triangles, arrays);

// Create instance (once per chunk)
Rid instanceRid = RenderingServer.InstanceCreate();
RenderingServer.InstanceSetBase(instanceRid, meshRid);
RenderingServer.InstanceSetScenario(instanceRid, GetWorld3D().Scenario);

// On chunk update: clear and re-add surface
RenderingServer.MeshClearSurfaces(meshRid);
RenderingServer.MeshAddSurfaceFromArrays(meshRid, ...);
```

This bypasses the scene tree for world geometry while still using Godot's renderer.

## Faithful port assessment

| Aspect | Faithfulness | Notes |
| --- | --- | --- |
| Visual appearance | ✓ | Same textures, can replicate lightmaps |
| Movement feel | ✓ | Collision uses original octree code |
| Performance | ✓+ | Modern GPU + LOD + culling = better |
| Editor preview | ✓+ | TOOL support exceeds original |
| Dynamic geometry | ✓ | Chunk-based updates, instant collision |

**Conclusion**: The ArrayMesh approach is sufficient for a faithful port. The
gameplay feel depends on movement physics and collision, which use the original
algorithms. Rendering differences are cosmetic and can be tuned to match.
